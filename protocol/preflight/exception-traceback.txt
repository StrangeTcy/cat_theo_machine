                -> trees.py:176  self.key_id = key.id

The object-id index is a red-black tree keyed on object identity, and its
lookup constructor reads `key.id` unconditionally. Every machine term in the
machine carries `.id`. A `Hypergraph` does not: it is a host object, not a
machine term. When a Hypergraph arrives at `_captured_object_id` as a
candidate, the lookup raises AttributeError instead of returning "not
captured", and the whole registration of the test aborts.

Why it looked load-sensitive, and why 109 was the magic number:

The candidate is `current.head.value` reached through root interning. Whether
that value is a Hypergraph depends on what the preceding registrations have
put in the graph. With 0, 16, or 32 predecessors the value is never a
Hypergraph and the run passes. The exact-109 set — every shard-0
registration before cursor 218 — is the first configuration tried that puts
a Hypergraph at that position. The count was never the mechanism; the
configuration was.

Not a defect in the test. Not a defect in the harness. The test did its job
and reported a failure; the guard swallowed the reason for ~the whole
history of the pin.

The guard was necessary and did its job: `_captured_object_id` no longer
raises. But it only removed the lookup-side failure. With the lookup
answering "not captured", the Hypergraph is queued for interning
(persistence.py:1365), the interning loop reaches it as `current`, and the
loop inserts every current into the same identity index
(persistence.py:1423) — where `IdentityRedBlackInsertMissing.__init__` reads
`key.id` at trees.py:425 and raises the same AttributeError.

The index has two doors, not one. Guarding the lookup alone moves the crash
from the read door to the write door.

Relevant facts for choosing the repair:

  - `Hypergraph` (graph.py:24) has `.rep` but no `.id`, `.value`, `.head`,
    `.tail`, `.inputs`, `.results`. It is the live session host object, not
    a machine term.
  - `_scalar_payload` already probes `x.id` (persistence.py:815) and, when
    absent, tries `_encode_scalar`, which handles only JSON-serialisable
    objects and mpz. A Hypergraph is neither, so `_scalar_payload` returns
    None — the same answer it returns for a real term. That conflation is
    why the Hypergraph reaches the index at all.
  - Three repairs are available and they are not equivalent. Skipping the
    object at the queue/loop boundary stops the crash but silently omits it
    from the snapshot. Encoding it as an opaque scalar preserves it but
    needs a type discriminator of the kind §0 forbids. Fixing upstream, so
    a live Hypergraph never enters machine state, addresses the cause. The
    choice is the operator's; it is not an engineering default.
