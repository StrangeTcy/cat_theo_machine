The object-id index is a red-black tree keyed on object identity, and its
lookup constructor reads `key.id` unconditionally. Every machine term in the
machine carries `.id`. A `Hypergraph` does not: it is a host object, not a
machine term. When a Hypergraph arrives at `_captured_object_id` as a
candidate, the lookup raises AttributeError instead of returning "not
captured", and the whole registration of the test aborts.

Why it looked load-sensitive, and why 109 was the magic number:

The candidate is `current.head.value` reached through root interning. Whether
that value is a Hypergraph depends on what the preceding registrations have
put in the graph. With 0, 16, or 32 predecessors the value is never a
Hypergraph and the run passes. The exact-109 set — every shard-0
registration before cursor 218 — is the first configuration tried that puts
a Hypergraph at that position. The count was never the mechanism; the
configuration was.

Not a defect in the test. Not a defect in the harness. The test did its job
and reported a failure; the guard swallowed the reason for ~the whole
history of the pin.
