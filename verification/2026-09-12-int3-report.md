## 4. Receipts: 15/15 transport-f faithful; the checker's syntactic line is luck

This section is the one judgment call of the admission, recorded in full
so no later session has to re-derive it.

Both live runs produced **15/15 worker receipt files** (3 submissions ×
5 modes), and transport is exactly faithful: submitted == received ==
searched for all 15 (the checker prints no transport FAIL), and worker
re-serialization is byte-identical to the coordinator's bytes
(`.request.wire` == `.received.wire`). Fix B works: workers spawn from
`prove` and carry the machine goal untouched.

What fails is the checker's further demand: each receipt goal must be
syntactically identical (`M.Compare`) to a goal parsed fresh from the
inputs in a separate process. Run 1 matched 5/15, run 2 matched 2/15;
the live script exits 1 at this step in both runs. The mismatch is
nondeterministic across processes for identical code and inputs.

Root cause, traced link by link (each link verified, not assumed):
parsing is stateless and identical (fresh vs sequential vs packs-booted
parses all Compare-equal); the dispatcher submits the parsed goal
unchanged; `CompareSearchModes` construction canonicalization is the
identity on `forall` goals; the wire codec round-trips faithfully. The
rearrangement happens in `Prove.__init__` (`proof.py:2936-2937`), which
normalizes **every** proof goal: `NormalizeKnowledge` →
`Canon.CanonicalTerm` → `M.CanonicalArithmeticTerm`, which sorts
`add`/`mul`/`eq` operands by `IdentityLess` (`core.py:223`,
`x.id < y.id` — machine-object creation order). Creation order varies
per process, so the canonical operand order varies per process: same
atoms, permuted subtrees. This behavior is pre-existing on both bases
(verified at `41e8078` and `55b773d`), intentional, and documented in
the code ("goal recognition compares equal up to commutativity"). None
of A/B/C touches it; fix B merely made it observable by producing the
first receipts ever to compare. The lane's 15/15 PASS on the same code
was a lucky creation-order coincidence, as was run 1's partial match.

Substance check: a deterministic probe re-canonicalizes each receipt
goal and its corpus goal under a content-ordered canonicalizer (add/mul
flattened, operands sorted by wire bytes). All six receipt goals across
both runs are **AC-equivalent** to their submitted goals
(`int3-receipts-ac-equivalence.txt`): the workers provably carry the
submitted goal up to the machine's own documented equivalence.

INT judgment: the worker-transport contract in the tag's scope — workers
spawn from `prove` and carry the goal faithfully — is MET
deterministically. The checker's syntactic-identity line demands more
than the machine's own contract and cannot pass deterministically on any
line carrying creation-ordered canonicalization. Admitting or blocking
on its exit code would both be ruling by luck. The candidate is admitted
on substance; the checker-vs-canonicalizer alignment (compare receipts
up to commutativity, or make the canonicalizer content-ordered) is
returned to the owning lanes as a **non-blocking follow-up**, with the
exact mechanism above. Re-running the live script until luck prints PASS
was deliberately not done: it would certify determinism that does not
exist.
