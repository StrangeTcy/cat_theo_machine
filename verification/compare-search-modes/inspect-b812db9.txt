RED TEST 1 — CompareSearchModesFillWarmsResidentPoolBeforeRootWaveTest
            (testsuite.py:9121; registered shard 0)
--------------------------------------------------------------------------
FAILING BRANCH: c2 — the only failing assertion. Observed:
  spawned                       = non-zero (Atom)          -> c1 clean
  _comparison_shared_root_candidates_ready = Diff (false) -> c2 FIRES
  workers                       = non-empty Pair          -> c3 clean
  states need root wave after   = false                   -> c4 clean

MECHANISM: the flag _comparison_shared_root_candidates_ready is
initialized to M.false_value (compare.py:69; probe __init__ in
testsuite.py:8695) and set to M.truth_value in exactly ONE place:
_comparison_cache_shared_root_candidates (compare_packets.py:1410), which
is invoked from _comparison_apply_shared_root_wave (compare_packets.py:1455)
in the real flow. _fill_parallel_workers (compare_executors.py:656) never
sets it. The test calls _fill_parallel_workers directly on a fresh probe,
so the flag stays false.

CLASSIFICATION: test-contract coupling mismatch. The test asserts "filling
the resident pool leaves the shared-root candidates cached", but caching is
a separate prepass (_comparison_apply_shared_root_wave ->
_comparison_cache_shared_root_candidates) that the production pipeline runs
before the fill, not inside it. Fix is either (a) the test also invokes the
prepass, or (b) _fill_parallel_workers is declared to own the caching and
the production flow's prepass is folded in. Ruling for the owner; not a
defect in the pool/fill mechanics themselves (spawn, worker list, and
root-wave-dispatch all behave).

RED TEST 2 — CompareSearchModesFindsReusableWorkerSnapshotDirTest
            (testsuite.py:8716; registered shard 1)
--------------------------------------------------------------------------
OBSERVED: _reusable_search_worker_result_paths(temp_dir) returns {}; no
"SearchBFS" key. The snapshot file IS written (os.path.exists = true) by
_search_worker_checkpoint. The resume matcher rejects it.

MECHANISM — two independent causes, both inside
_search_worker_snapshot_matches_current_problem (compare_subprocess.py:319):

  cause (a) heuristic source mismatch:
    the checkpoint stores _search_worker_mode_heuristic(runtime, "bfs", ...)
    (main.py:521) which is built from runtime.theorem_heuristic, while the
    resume matcher compares against _heuristic_for_mode(BFSLabel)
    (compare_attempts.py:324) which is built from the compare probe's
    self.heuristic. Different bases -> the stored heuristic never equals
    the compared heuristic. Observed: TermEqual(worker_heuristic,
    _heuristic_for_mode(BFSLabel)) = false.

  cause (b) codec TermEqual identity gap:
    the snapshot round-trip (SnapshotCodec.capture -> load) reconstructs
    the attempt's start/goal terms as fresh objects. Observed:
      M.Compare(loaded_start, start)  = truth  (content-equal)
      M.TermEqual(loaded_start, start) = false  (identity-sensitive)
    The matcher uses M.TermEqual (compare_subprocess.py:321-326) for
    start, goal, and heuristic, so a content-identical restored term is
    rejected. Char atoms are not re-interned by the codec round-trip.

CLASSIFICATION: real resume-reuse defect. The worker-snapshot reuse path
cannot currently match ANY freshly-written snapshot, because the matcher
compares identity-sensitive terms against freshly reconstructed codec
output and against a differently-sourced heuristic. This is the
"snapshot coverage / fresh-process restore equivalence" gap named in the
brief; it is a genuine defect, not a test expectation problem.
